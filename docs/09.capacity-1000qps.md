# 09. 容量：按 1000 QPS 给每个环节定预算

日期：2026-11-16。状态：**全部是估算**，没有压测。每个数字后面都要用 `docs/09` 末尾的压测步骤换成实测值。

## 结论

1. 1000 QPS 的第一个瓶颈是**公网带宽**，不是集群。Domestic 峰值 100 Mbps，平均响应 10 KB 时 1000 QPS 就要约 80 Mbps。
2. 第二个瓶颈是**后端里慢的那几个**：HanLP 分词、向量化、大模型调用、读 NAS 冷文件。它们的上限是几十每秒，要靠缓存、异步和单独限流，不能指望扩到 1000。
3. 网关、普通 API、PostgreSQL 在现有硬件上都有余量。

## "1000 QPS"指什么

先约定口径，否则每个环节的数字对不上：

| 流量类型 | 占比（假设） | 峰值 | 说明 |
|---|---|---|---|
| 普通 API（读，JSON 小响应） | 70% | 700/s | 列表、详情、权限、配置 |
| 普通 API（写） | 10% | 100/s | 入库、下单、状态变更 |
| 搜索 | 10% | 100/s | 要过分词和 ES。Hub 图册里已把 100 QPS 列为待压测目标 |
| 静态文件 | 10% | 100/s | 图片为主，走缓存 |
| 大模型 / RAG 生成 | 不计入 | 单独限流 | 按并发数算，不按 QPS 算 |

占比是为了能算数而假设的。有了真实访问日志后替换这张表。

## 每个环节的预算

| 环节 | 1000 QPS 时的负载 | 现有能力（估算） | 结论 | 措施 |
|---|---|---|---|---|
| 公网带宽 | 响应平均 10 KB → 约 80 Mbps；100 KB → 约 800 Mbps | Domestic 峰值 100 Mbps，不是持续保证 | **不够** | 压缩；静态文件走 CDN；云服务器带宽 ≥ 200 Mbps |
| 边缘 Nginx | 1000 请求每秒，长连接下 TLS 握手远少于此 | 2 vCPU 能转发，但 4G 内存下缓存和连接数要限制 | 勉强 | 开 keepalive 和 HTTP/2；云服务器到位后分担 |
| 隧道 | 同带宽 | WireGuard 内核态，远高于 100 Mbps；OpenVPN 用户态，没测 | WireGuard 够 | 业务流量只走 WireGuard |
| 宿主机 Nginx | 1000/s 转发 | 128 核机器上不构成负载 | 够 | 上游开 keepalive |
| 集群网关 | 1000/s | 每个副本每核数千 | 够 | 2 副本起步，按 CPU 扩 |
| 普通 API（Node.js） | 800/s | 单进程 1000 到 3000 每秒（简单接口）；有数据库查询时更低 | 要多副本 | 每个服务 ≥ 3 副本，HPA 上限 8 |
| PostgreSQL | 每请求 3 条查询 → 约 2400 条每秒，其中写约 300 | 16 核 48G 的实例远高于此 | 够 | 连接池（事务模式）限制总连接数；重查询走只读入口 |
| Elasticsearch | 100 次搜索每秒 | 取决于索引大小和查询，没测 | **未知** | 单独压测 |
| HanLP | 100 次查询分词每秒 | 5 个 worker，每次推理几十到几百毫秒 → 几十每秒 | **不够** | 已有的查询合并和结果缓存；超时降级到 jieba（已实现）；高频词预热 |
| Embedding | 只在 RAG 查询和入库时调用 | 单卡，批量处理 | 不按 QPS 算 | 查询向量缓存；入库走队列 |
| 大模型 | — | 受上游配额限制 | 单独限流 | 按租户限并发，排队 |
| 静态文件 | 100/s | 本机盘加 Nginx 缓存：上万；NAS 冷读：约 12 每秒 | 热的够，冷的不够 | 见 `docs/07`，把冷读压到接近 0 |
| SSO 内省 | 每个带 token 的请求 | Hub 缓存 30 秒 | 够 | Launcher 在 s1，L2 的服务必须缓存内省结果，不能每个请求都回 s1 |

| 组件 | 副本 | 每副本 CPU / 内存（request） | 小计 |
|---|---|---|---|
| 集群网关 | 2 | 1 核 / 512M | 2 核 / 1G |
| pg-common | 1 | 16 核 / 48G | 16 核 / 48G |
| pg-pay | 1 | 2 核 / 4G | 2 核 / 4G |
| Elasticsearch | 1 | 8 核 / 32G | 8 核 / 32G |
| Redis | 1 | 1 核 / 2G | 1 核 / 2G |
| HanLP | 1 | 16 核 / 24G（按实测常驻量，不是 1G） | 16 核 / 24G |
| Hub（6 个工作负载） | 各 2 到 3 | 约 1 核 / 1G | 约 16 核 / 16G |
| DataPort、Pay、Rig | 各 2 | 约 1 核 / 1G | 约 6 核 / 6G |
| mx-static | 2 | 2 核 / 2G | 4 核 / 4G |
| 系统和余量 | — | — | 留 30% |
| **合计** | | | **约 71 核 / 137G**，占 128 核的 55%、256G 的 54% |

pg-common 和 HanLP 的数字抄自 L1 的现行配置（16 CPU / 48Gi；limit 32Gi）。其余是估计。这张表说明阶段 A 把这些都放 s2 是放得下的，但余量不大，embedding 和 ocr 重开之前要先看实际占用。

## 限流和降级放在哪

| 位置 | 做什么 |
|---|---|
| 边缘 Nginx | 按来源地址限速和限连接数；超大请求体拒绝 |
| 宿主机 Nginx | 对慢上游设连接上限，防止一个慢服务占满转发连接 |
| 应用 | 按租户 / API Key 的配额（Hub 已有）；对 HanLP、大模型的调用设并发上限和超时 |
| 数据库 | 连接池上限；语句超时；只读入口单独的超时 |

原则：慢的东西要有上限和排队，超过就快速返回 429 或降级结果，不能让它把前面的层堵住。L1 的 504 排查（launcher docs/60）就是慢后端把入口拖超时。

## 压测步骤（还没做）

工具用 k6，脚本以后放 `scripts/loadtest/`。

1. **基线**：对 s2 上的样板服务（`templates/project` 部署出来的），从 LAN 直接打宿主机 Nginx。量出"宿主机 Nginx → 网关 → Pod"这一段的上限。
2. **加隧道**：从 Domestic 经 WireGuard 打同一个服务。差值就是隧道和边缘的开销。
3. **加数据库**：打一个读库的接口和一个写库的接口。
4. **真实服务**：Hub 的列表、详情、搜索各一个接口，按上面的占比混合。
5. 每一步记录：QPS、P50 / P95 / P99 延迟、错误率、各层 CPU 和带宽。结果写成新的一篇文档，替换这里的估算。

压测只在 s2 和测试命名空间做。**不对 s1 和 Launcher 的接口压测。**
