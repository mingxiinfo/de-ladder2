# 60. mincave.minsight-ai.com 默认全部放行

日期：2026-11-22。状态：决策，已实现，在 nginx 1.27.5 容器里测过两种模式。没有推到 domestic02。 2026-11-25：默认值已被 `docs/61` 取代：全部放行的是管理域名 `v2.launcher.minsight-ai.com`，`mincave.minsight-ai.com` 改回只放客户端接口。

用户 2026-11-22：不需要拦截太紧，因为后续可能还要加，比如让 `/admin/`、`/internal/` 等等都放行，这样后续也可以在这些下面做功能，不用每次 admin allow。参照 V1，把它目前有的路由都放行。

同时贴了 domestic02 的访问日志：三次 `GET /admin/` 都来自 `18.181.103.67`，是用户代理的出口（AWS 的地址），不是本机以为的公网地址。

本篇取代 `docs/59` 第 3 条"管理后台默认在公网上关着"。

## 结论

1. **默认 `open`：Launcher 的所有路由经 domestic02 对公网开着，鉴权交给 Launcher 自己。**
   - `/admin/`、`/internal/`、`/readyz` 等，以后在它们下面加的新路由也一样，不用再改站点。
   - 第一次验证（`docs/59`）的问题也就没了：代理出口一变，按 IP 放行就失效。
2. **`restricted` 模式还在，一条命令切回去：**
   ```bash
   ./scripts/manage.sh relay domestic02 site --access restricted --admin-allow <IP,...>
   ```
   切回去以后，只有 v1 的客户端接口对所有人开，其余只给登记的来源。`--access open` 再放开。模式记在推送机上（edge state 里的 `ladder2-access`），不进 Git。
3. **放开以后要知道的：v1 里 `/internal/*` 只在内网能到，不少写接口自己不做鉴权。**
   - 按处理函数里有没有令牌、Bearer、lease capability 检查粗略数了一遍，可能有误报：
     - DNS 13 个写接口全没有：建路由、删路由、发布；
     - Config Center 16 个里 13 个没有：secret provider / reference、网关运行配置、功能开关；
     - Release 10 个里 6 个、Test Center 3 个全没有、AppCenter 5 个里 2 个；
     - site-slots、launcher-network、MinCave、service-operations 的写接口都有检查。
   - 也就是说，知道地址的人能在 s2 那套上增删 DNS 路由、改网关配置。
   - 现在能接受，是因为 s2 那套是复刻，用户流量还在 s1（`docs/36`）；而且 SSH 只能到 domestic02（`docs/53`），site-slot 的写接口都有鉴权。
   - **切换用户流量之前必须补上：** 要么给这些接口加鉴权，要么切回 `restricted`。`docs/15` 第 78 项。
4. 站点其余不变：
   - `/healthz` 由 domestic02 自己回，`/bootstrap-healthz` 转给 Launcher；
   - 转给 s2 时用真实地址覆盖 `X-Forwarded-For`，并带 `domestic-edge`；
   - 证书在 s2 上签和续；
   - `/ladder2-whoami` 显示这台看到的来源（`restricted` 时用得上）。
