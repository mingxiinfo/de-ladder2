## 增长规划

三个盘都在 55% 到 61%，增速快。但现在没有历史数据，说不出还能撑多久。所以第一步是开始记录：

```bash
./scripts/manage.sh disk record    # 把当前各挂载点的用量追加到状态文件。在每台服务器上每天定时跑
./scripts/manage.sh disk trend     # 按最近的记录算每天增长多少、到 80% 还有几天
```

有了两周的数据之后，下面这张表才能填实际数字：

| 盘 | 到 80% 的余量 | 增长来源（推测） | 措施，按先后 |
|---|---|---|---|
| s1 `/` | 约 210G | 镜像、构建缓存、mx-move 的历史副本、容器日志 | ① 清构建缓存和不用的镜像 ② 业务验收过的 mx-move 历史副本由人确认后清理 ③ 新服务都部署到 s2 |
| s1 `/home` | 约 230G | 待确认 | 先查清是什么 |
| s1 `/data` | 约 400G | 数据库、Docker 卷、采集的原始数据 | ① Hub 的数据面搬到 s2 ② 冷数据归档到 NAS ③ 宿主机 PG 搬走（见下） |
| NAS | 约 19T | 媒体 | 余量大。但它是机械盘单点，放的东西越多越要考虑它自身的保护 |

规则：

- **告警线 70%，行动线 80%。** 到 70% 开始按上表做，不等到 90%。xfs 写满后恢复很麻烦，L1 已经为存储问题出过一次事故。
- 每个会增长的目录有一个负责的项目。`du` 出来没人认领的大目录，先问再动。
- 容器日志设大小上限和轮转。镜像和构建缓存定期清理（L1 用的是保留 2GB / 24 小时）。
- s2 上线后，新增的东西默认放 s2。s1 只减不增。

## 宿主机 PostgreSQL 搬到哪

背景：s1 的 `127.0.0.1:5432` 是 Night-All / po-infra 的源数据，Hub 的清洗计划依赖它。它只监听回环地址，这是把 Hub 搬到 s2 的障碍。用户的想法是起一个数据放在 NAS 上的 PostgreSQL 服务，把这块业务迁过去，因为 Hub 对这个库的读写要求不高。

**方向同意：把它从"s1 宿主机上只听回环的进程"变成"集群里一个有名字的服务"。** 数据放 NAS 可以做，但要清楚代价，并且我建议先选另一个位置。

### 数据库放 NFS 的实际情况

PostgreSQL 官方文档允许放在 NFS 上，条件是硬挂载、服务端同步写。现在的挂载参数（`hard`、`proto=tcp`）满足客户端这一半；NAS 导出是不是同步写要在 NAS 上确认。

| 风险 | 说明 |
|---|---|
| NAS 不可达时数据库卡死 | `hard` 挂载下所有读写挂住，数据库不报错也不响应，依赖它的 Hub 清洗任务跟着挂住。恢复后通常能继续 |
| 慢 | NAS 是机械盘、内存小。每次提交都要等 NAS 落盘，批量清洗时会很明显 |
| 不能两个实例同时用同一个数据目录 | 误启第二个实例会损坏数据。必须保证只有一个 Pod，不能配多副本 |
| 备份在同一台 NAS 上就不算备份 | 这个库的备份要放别处 |

"读写要求不高"能接受前两条。后两条靠配置避免。

### 建议

| 方案 | 做法 | 适合 |
|---|---|---|
| A. s2 本机盘（**建议**） | 集群里起一个 PostgreSQL，卷在 s2 的 `/data`，每天备份到 NAS | 这个库不大（几百 G 以内）。s2 有约 2T 空盘，没理由不用快盘 |
| B. 冷热分开 | 当前在用的库放 s2 本机盘；历史的、不再写入的原始数据导出成文件归档到 NAS | 库很大，但大部分是不再访问的历史数据 |
| C. 整个放 NAS | 集群里起一个单副本 PostgreSQL，卷是 NAS 上的目录 | 库很大，而且都要在线可查，本机盘放不下 |

选哪个取决于**这个库有多大、每天增长多少**，现在不知道（`docs/15`）。在 s1 上查：

```sql
SELECT datname, pg_size_pretty(pg_database_size(datname)) FROM pg_database ORDER BY pg_database_size(datname) DESC;
```

不管选哪个，迁移步骤相同：在新位置建实例 → 复制数据 → Hub 的清洗任务改连接串指向新服务的集群内域名 → Night-All / po-infra 改连接串 → 旧实例停掉保留。连接串里写的是服务名，以后再换位置不用改应用。

规则的表述相应修订：**数据库默认不放 NFS。确实要放的，在 `inventory/projects.yaml` 里登记为冷库，单副本，备份放别处。** etcd 和 SQLite 仍然不放。

## 业务怎么读写 NAS

修订上一轮的想法：mx-static 是之前的设计，考虑还不周全，**不把它定为所有项目读写文件的必经之路**。业务方有自己读 NAS 的方式，这没有问题。平台这一层要提供的是让各种方式都更快、更稳的基础条件：

| 平台提供 | 内容 |
|---|---|
| 统一的挂载 | 每个节点 `/mnt/nas` 用同一行 fstab；集群里用一个 NFS 的 PersistentVolume 按项目子目录分配，Pod 不直接写主机路径 |
| 目录约定 | `/mnt/nas/<项目>/`，一个项目一个顶层目录，权限按项目的用户分。备份在 `/mnt/nas/backup/` |
| 本机缓存盘 | 每个节点的 `/data/cache/<项目>/`。热文件放这里，NAS 只当冷存储 |
| 入口缓存 | 宿主机 Nginx 的缓存，按路径配置，项目不用改代码就能用 |
| 对外分发 | 要公开的文件同步到 OSS 加 CDN 的任务模板 |
| 读 NAS 的超时约定 | 请求路径上读 NAS 必须有超时，因为 NAS 不可达时读操作会挂住 |

三种读法，由项目按自己的情况选：

| 读法 | 延迟 | 适合 |
|---|---|---|
| 直接读 `/mnt/nas` | 高，机械盘随机读 | 批处理、离线任务、偶尔访问的归档 |
| 本机缓存，未命中再读 NAS 并回填 | 命中时和本机盘一样 | 在线服务。mx-static 的 reader 是这种模式的一个现成实现，可以用也可以自己写 |
| 经 Nginx 缓存或 CDN | 最低 | 给浏览器的图片和视频 |

mx-static 的定位改为：**一个可选的基础服务**。它的流式下载、内容哈希去重、签名链接这些能力谁需要谁接。上线不再排进迁移路线的必经步骤。

### 图片向量化

有人提出做图片向量化。架构上需要准备的：

- **GPU**：规划每台服务器 2 块 RTX 5090（现在 4 块全在 s1，`docs/21`）。集群里装 NVIDIA 设备插件，向量化服务声明要一块卡，调度器来分配。现在 mx-embedding 和 mx-ocr 是 Compose，各占一块；进集群后和图片向量化排队用卡。
- **批处理而不是在线**：给存量图片算向量是离线任务，从 NAS 顺序读（机械盘顺序读不慢），结果写数据库。走 mx-common 已有的 PostgreSQL 任务队列，不新加中间件。
- **向量存哪**：Hub 现在把向量存在 PostgreSQL 的数组列里，用 Elasticsearch 的 `dense_vector` 做近邻检索。图片向量沿用同一套，不引入专门的向量数据库。量到千万级再评估。
- **模型文件**：放 `/data/models`，不放 NAS。mx-embedding 上次因为磁盘读写问题停掉，模型加载和数据库抢同一块盘是可能的原因之一。

这些是平台要备好的条件。向量化服务本身是业务项目，按 `docs/10` 接入。

## 平台服务和业务的边界

HanLP 分词保留，以后大概率会用（比如用户名搜索时列出相近的用户名，这类模糊匹配 Elasticsearch 能做）。为了不把业务和架构绑死：

| 平台提供（有地址、有容量、有备份） | 业务自己决定 |
|---|---|
| PostgreSQL 实例，每个项目一个库 | 表结构、迁移、查询 |
| Elasticsearch 集群，每个项目一个索引前缀 | 索引定义、分词方式、查询 |
| HanLP 分词服务，一个 HTTP 地址 | 调不调、超时后降级到什么 |
| Redis | 缓存什么 |
| GPU 和模型服务（embedding、ocr） | 用哪个模型、什么时候调 |
| NAS 目录、本机缓存盘 | 文件怎么组织 |

平台不知道也不关心"用户名搜索"这个需求。它只保证 Elasticsearch 和 HanLP 在那里、能扛住约定的调用量。HanLP 的并发上限（现在 5 个 worker）是平台公布的容量，业务按这个上限设计调用方式：能缓存的缓存，能批量的批量。

Hub 现在能到约 100 QPS（用户口述，调整后的结果）。这个数字记作 Hub 的现状，替换 `docs/09` 里"搜索 100 QPS 待压测"的说法；HanLP 和 NAS 冷读仍然是那两个明确的慢点。
