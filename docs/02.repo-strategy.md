# 02. 仓库策略：原地升级还是拷贝过来

日期：2026-11-16。状态：决策，尚未执行任何拷贝。

## 结论

**两个都不做。** 不在 L1 仓库里原地升级，也不把项目整批拷贝过来。`de-ladder2` 是一个新的平台仓库，对 L1 的项目采用"登记、适配、按需接管"。

## 为什么不原地升级

- L1 是 MX-H2I 的现役环境，脚本里写死了单节点假设：hostPath PV、磁盘 UUID 和集群 UID 的身份保护、`mx-move` 的 bind 挂载、`imagePullPolicy: Never` 加本机导入镜像。这些保护在单机上是对的，改成多节点就要全部重写，而每改一处都可能碰到 H2I 的登录和联网。
- L1 的 `scripts/manage.sh deploy all` 明确只支持"原 Internal 主机"，文档自己写着多机发现和换机恢复没有实现。
- 新集群需要一段时间和旧集群并存。两套做法放在同一个仓库的同一批脚本里，很难看出哪条命令作用在哪台机器。

## 为什么不整批拷贝

- 业务源码有两份就会分叉。L1 仓库还在每天提交（最近的提交是 mincave 的界面修复）。
- 拷过来的大部分东西在新集群上用不到：`mx-launcher/scripts` 里 80 多个脚本多数是单节点恢复工具。

## 三类项目

| 类别 | 包括 | 源码在哪 | 本工程里有什么 |
|---|---|---|---|
| 平台（本工程负责） | 集群、网关、数据库运行时、存储、备份、隧道、mx-static、mx-embedding / mx-ocr 的部署 | 新写的在本工程；mx-static 等在真正迁移那天拷入，并记下来源提交号 | 清单、脚本、文档 |
| MX 业务项目 | mx-launcher、mx-insight-hub、mx-dataport、mx-pay、mx-rig | 留在 L1 仓库 | `inventory/projects.yaml` 里的登记；部署清单放部署仓（见下） |
| 外部项目 | Night-All、po-backend-java、po-infra、Luopan、其他人的项目 | 各自的仓库 | 登记，加上宿主机 Nginx 的转发配置 |

"按需接管"的规则：一个组件只有在**要改成多节点形态**的那一步才拷进来，拷的时候在它的 README 第一行写明来源路径和提交号。在那之前只引用路径。

## 借鉴 L1 的哪些工程做法

这些做法在 L1 里已经被事故验证过，L2 直接沿用：

| 做法 | L1 的出处 | L2 怎么用 |
|---|---|---|
| `plan` 离线显示要做什么，`status` / `doctor` 只读 | `electron-dock/scripts/manage.sh` | `scripts/manage.sh` 同样分只读和写入，写入必须指名目标 |
| 文档区分"源码里有"和"线上已验证" | 每篇文档的状态行 | 每篇文档第一段写状态；清单没上过集群就写"没测" |
| 查询失败显示 UNKNOWN，不当成"未部署" | `mx-base/scripts/manage.sh` | 同 |
| 迁移只复制不删除，事务记录可续跑 | `mx-move` | 数据库和文件迁移都按这个来 |
| 数据库模板变化不自动重启数据库 | PG StatefulSet 用 OnDelete | CloudNativePG 的主库切换设成受控（docs/06） |
| 任务和业务数据同一个事务提交，队列放 PG | `mx-common` README | 不为队列引入新中间件 |
| 搜索索引是 PG 的可重建投影 | `mx-common`、Hub 图册 | ES 不做备份优先级最高的对象，PG 才是 |
| 部署互斥锁加结果记录 | `~/.local/state/mx-electron-dock` | 后续实现时沿用，状态目录换名 |
| 编号文档只增不改写 | `mx-launcher/docs/00-63` | `docs/NN.xxx.md`，新决策新增一篇 |

不沿用的：把运行时身份（磁盘 UUID、集群 UID）写进各项目脚本逐个校验。多节点下这件事交给集群和 Operator。

## 别人的项目放哪

本工程定位是集群架构和自身业务。其他人的项目要进集群或直接部署，清单放部署仓 `/Users/qpjoy/workspace/mingxi/de-mingxi/`：

```text
de-mingxi/
├── compass/deploy/          # 已有：Domestic 443 网关、Internal Nginx
└── projects/
    ├── wechat-message-hub/  # 已有
    └── de-ladder2/          # 新建：每个进 L2 的项目一个目录
        ├── manage.sh        # 部署仓自己的入口，被本工程的 scripts/manage.sh 转调
        ├── mx-insight-hub/
        │   ├── base/        # kustomize base
        │   └── overlays/{staging,production}/
        ├── mx-pay/
        └── night-all/       # 不上 k8s 的项目：放 nginx 转发片段和 systemd / compose 文件
```

分工：

- 项目的人负责：镜像、自己目录下的清单、数据库迁移脚本。谁开发谁部署不变。
- 平台负责：命名空间、配额、网关、数据库实例、备份、域名接入，以及一份项目模板（`templates/project/`）。

目录约定和接入步骤见 `docs/10.project-onboarding.md`。部署仓里的 `projects/de-ladder2/` 目前还没建。
