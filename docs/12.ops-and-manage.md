# 12. 运维入口：manage.sh 的约定

日期：2026-11-16；2026-11-17 更新命令表，第三轮加 `probe`。状态：只读和离线命令可用；写集群的命令没在真实集群上跑过；`node prepare|join`、`backup run`、`restore` 没有实现。

## 一个入口

```bash
./scripts/manage.sh help
```

所有部署和编译都从这里进。子项目保留自己的 `manage.sh`，外层只负责找到它并把命令转过去，不重写子项目的逻辑。这是 L1 `electron-dock/scripts/manage.sh` 的做法：薄入口，各项目继续负责自己的迁移、凭据和就绪检查。

## 命令

| 命令 | 作用 | 读写 | 现状 |
|---|---|---|---|
| `help` | 列出全部命令 | — | 有 |
| `list` | 列出 `inventory/projects.yaml` 里登记的项目、类别、迁移状态、路径是否存在 | 只读 | 有 |
| `hosts` | 列出登记的主机 | 只读 | 有 |
| `docs` | 列出 `docs/` 的文档和状态行 | 只读 | 有 |

| `doctor` | 检查本机工具，和（在服务器上运行时）磁盘、NAS 挂载、端口归属 | 只读 | 有（工具和本机检查） |
| `k8s render <目录>` | 打印渲染后的清单 | 只读 | 有 |

| `node prepare\|join <主机>` | 通过 SSH 准备机器、加入 | **写** | **没有** |
| `backup plan` | 备份什么、放哪（`docs/19`） | 只读 | 有 |
| `backup run\|list\|verify`、`restore plan\|run` | 备份和还原 | **写** | **没有** |
| `disk record`、`disk trend` | 记录本机磁盘用量；算增长和余量（`docs/20`） | 写本地状态文件 | 有，没在服务器上跑过 |
| `probe url <地址> [--host <域名>]` | 测一个地址各阶段的耗时：DNS、建连、TLS、等首字节、传输（`docs/26`） | 只读，只发 GET | 有，只在开发机上对公网地址跑过 |
| `probe list`、`probe route <名字>` | 按 `inventory/probes.yaml` 逐层测一条链路，算每层的开销 | 只读 | 有，没对真实链路跑过 |
| `probe wg` | 本机 WireGuard 各对端最近握手时间（`docs/24`） | 只读 | 有，没在装了 WireGuard 的机器上跑过 |
| `l1 <命令...>` | 转调 L1 的 `electron-dock/scripts/manage.sh`，只放行 `list`、`plan`、`status`、`doctor` | 只读 | 有 |
| `run <项目> <命令...>` | 转调某个登记项目自己的 `manage.sh` | 取决于子命令 | 有 |
| `diagrams` | 生成图册（见 `docs/13`） | 写本地文件 | 有（需要先装 archify） |
| `loadtest` | 压测 | — | **没有**，规划中 |

## 规矩

这些是从 L1 的事故里学来的，写进脚本，不只是写在文档里：

1. **写集群的命令必须带 `--context`。** 不使用当前默认的 kubectl context。s1 和 s2 是两个集群，默认 context 指向哪个全凭上一次操作。
2. **`l1` 子命令只放行只读命令。** 要在 s1 上部署，登录 s1 用 L1 自己的入口，不从这里转。这样本工程不可能误触发 L1 的发布。
3. **只读命令永远不改任何东西**，包括不"顺手修复"。L1 特意把 `status` 和会修 endpoint 的命令分开。
4. **查不到就说查不到。** 连不上集群显示 UNKNOWN 并返回非零，不显示成"未部署"。
5. **写操作先显示差异。** `app apply` 先打印 `kubectl diff` 再执行，日常发布不要求输入确认（`docs/16`：内部自用，门槛从简）。装平台组件和还原仍要输入 `yes`。
6. **没有"全部部署"和"全部停止"。** 也没有删数据的命令。
7. **凭据不出现在命令行参数和输出里。**
8. 入口不提供自动回滚。失败时保留现场和记录，由人按文档处理。

## 子项目的 manage.sh

外层怎么找到它：`inventory/projects.yaml` 里每个项目的 `path` 加 `scripts/manage.sh`。

子项目的 `manage.sh` 最好支持这几个命令，外层的 `list` 和 `status` 才能统一显示：

| 命令 | 含义 |
|---|---|
| `status` | 只读，退出码 0 表示健康 |
| `plan` | 离线显示 `deploy` 将要做什么 |
| `deploy` | 部署 |
| `build` | 只构建 |

L1 的项目已经基本符合。不符合的项目外层照样能用 `run` 转调，只是不出现在汇总里。

## 状态和记录

- 部署记录放 `~/.local/state/de-ladder2/`，目录权限 0700，每次写操作一个 JSON：项目、目标集群、开始和结束时间、退出码。沿用 L1 的格式。
- 同一台机器同一个用户同时只允许一个写操作（文件锁）。这把锁管不到别的机器和别的用户，不要把它当成集群级的锁。
- 这部分**还没实现**，实现第一个会写集群的业务部署时一起做。

## 从哪台机器运行

| 命令 | 在哪运行 |
|---|---|
| `list`、`docs`、`check`、`k8s render` | 任何有这个仓库的机器，包括开发机 |
| `probe` | 任何机器。从哪台跑，测的就是从那台出发的耗时；内网各层的地址只有在内网才通 |
| `doctor` 的磁盘、NAS、端口检查 | 在被检查的服务器上 |
| `k8s platform`、`app apply` | 能连到目标集群 apiserver 的机器。建议固定用 s2 |
| 构建镜像 | s2，或以后的构建机 |
