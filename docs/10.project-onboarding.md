## 项目分两类

### 能上 k8s 的

要求（接入检查表）：

- [ ] 有镜像，标签不用 `latest`。
- [ ] 进程无状态：本地不存必须保留的文件。要存文件用 mx-static 或声明卷。
- [ ] 配置从环境变量或挂载的文件读，不写死地址。
- [ ] 有就绪检查接口。数据库连不上时就绪检查失败，进程不退出。
- [ ] 收到 SIGTERM 后能在 30 秒内处理完在途请求再退出。
- [ ] 数据库迁移是一个独立的 Job，可以重复执行。
- [ ] 写了 CPU 和内存的 request（HPA 按 request 的百分比算）。
- [ ] 日志写到标准输出。

步骤：

1. 平台登记：在 `inventory/projects.yaml` 加一条；建命名空间（带 `ladder2/gateway: main` 标签）、配额、数据库和账号。
2. 项目的人把 `templates/project/` 拷到部署仓的 `<项目>/`，替换名字、镜像、端口、域名。
3. `./scripts/manage.sh app render <项目> staging` 看渲染结果；`app apply <项目> staging --context <集群>` 部署到测试环境。
4. 验收后同样的命令部署 production。
5. 平台在宿主机 Nginx 和边缘 Nginx 加这个域名的转发。

### 暂时上不了 k8s 的

Night-All、po-infra、po-backend-java 属于这类，以后还会有。它们不需要改造，只需要**登记清楚**：

- [ ] 在 `inventory/projects.yaml` 有一条：在哪台机器、哪个目录、监听哪个端口、依赖什么。
- [ ] 监听 `127.0.0.1` 或 LAN 地址，不占 80、443、30080 和其他已登记的端口。
- [ ] 有开机自启（systemd 或 Compose 的 restart 策略）。
- [ ] 有一个健康检查地址，`./scripts/manage.sh status` 能探测到。
- [ ] 宿主机 Nginx 的转发片段放在部署仓。
- [ ] 数据在哪、怎么备份，写在它的 README 里。

这类项目通过宿主机 Nginx 对外，不经过集群网关。集群里的服务要调它时，平台在集群里建一个指向它的 Service（见 `docs/05`）。

以后要迁进集群时，按上面"能上 k8s 的"检查表补齐，然后只改宿主机 Nginx 里那个域名的上游。

## 命名约定

| 对象 | 规则 | 例子 |
|---|---|---|
| 命名空间 | 项目名；测试环境加 `-staging` | `mx-pay`、`mx-pay-staging` |
| 数据库 | 一个项目一个库一个角色，名字用下划线 | 库 `mx_insight_hub`，角色 `mx_insight_hub` |
| 域名 | 正式 `<名>.minsight-ai.com`；测试 `<名>.staging.<内网域名>` | 内网域名待定 |
| 镜像标签 | 提交号或版本号 | `mx-pay:1.4.2`、`hub:8f3c2a1` |
| Secret | `<项目>-<用途>`，不进 Git | `mx-pay-db`、`hub-sso-client` |

## 凭据

- Git 里不放任何密码、token、私钥。清单里只引用 Secret 的名字。
- Secret 由平台在集群里创建，原始值存在服务器上权限 0600 的文件里，并纳入加密备份（`docs/06` 第 5 层）。
- 测试环境和正式环境的凭据不同。
- SSO 客户端的登记在 Launcher（L1 的 `identity-app.mjs`）做，登记时填 L2 的回调地址。**不改已有客户端的配置。**

## 镜像怎么到节点上

L1 的做法是在节点上构建，再导入本机 containerd，清单里写 `imagePullPolicy: Never`。单节点可行，多节点就要每台都导入。

L2 的做法：

- 阶段 A（一台）：可以继续"构建后导入"，k3s 支持把镜像 tar 放进它的导入目录。
- 阶段 B 之前：起一个内网镜像仓库（放 s2，数据在 `/data`），k3s 的 `registries.yaml` 指向它。构建机推送，节点拉取。
- 构建时出网用的代理（L1 的 `PROXY=127.0.0.1:7788`）只用于构建，不进运行环境。

镜像仓库选哪个（Docker 官方的 registry 镜像还是 Harbor）没定。部署仓里有 `HARBOR.md`，说明以前考虑过 Harbor。
